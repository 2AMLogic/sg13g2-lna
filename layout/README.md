# layout/

Layout and DRC/LVS evidence for this block. The first content here is the
**toolchain bring-up of issue #63**: the cascode core and the DR-0003 bias
island, drawn from the PDK's own PyCells by a committed script, then checked
with `klt drc`, `klt extract` and `klt lvs`. This is a partial, parameterised
layout. It is not the block's layout, and none of the results below is a
signoff verdict. See "What the evidence supports" before citing anything.

```
layout/
  README.md                     this file
  run_flow.sh                   regenerate everything below, in order
  pcell_env.py                  loads IHP's SG13_dev PyCell library headless
  lvs_reference.py              derives the scoped LVS reference from design/netlist/lna.spice
  tools/fetch-pcell-deps.sh     fetches the two PyCell submodule shims (pinned, sha256-checked)
  build/                        fetched shims (gitignored, generated)
  lna_core/
    realization.json            scope: which netlist instances are drawn, and as which PDK device
    generate.py                 draws lna_core.gds (--nx = issue #58's emitter-count knob)
    lna_core.gds                committed, byte-deterministic output of generate.py
    lna_core.provenance.json    GDS sha256, nx, PyCell library hash, shim commits, klayout version
    lna_core.lvs_reference.spice  generated by lvs_reference.py
    lvs_request.json            klt lvs request: scoped reference
    lvs_full_request.json       klt lvs request: design/netlist/lna.spice as-is
    klt_version.json            `klt version` of the build that produced the four reports
    drc_report.json             klt drc --deck sg13g2
    extract_report.json         klt extract --deck sg13g2
    lna_core.extracted.spice    the netlist that extraction wrote
    lvs_report.json             klt lvs vs the scoped reference
    lvs_full_report.json        klt lvs vs design/netlist/lna.spice
```

## Scope

`lna_core/realization.json` is the single statement of scope. It must
partition `design/netlist/lna.spice` exactly: `lvs_reference.py` fails if
any netlist instance is in neither list, in both, or names a device the
netlist no longer has.

**Drawn (6 of 30 instances):**

| Instance | Drawn as (PDK PyCell) | Role |
|---|---|---|
| `XQ1`, `XQ2` | `npn13G2`, `Nx` = the `nx` parameter (default 8, the netlist's value) | cascode core |
| `XQ3` | `npn13G2`, `Nx=1` | DR-0003 island: diode-tied density-match reference |
| `R3b` | `rppd` w=1u l=1.005u | DR-0003 island: `bref` to `b1` coupling. The PyCell's own model readout for this geometry is 329.74 Ω against the schematic's ideal 330 Ω |
| `Cbref` | 16 × `cmim` 64.5 × 64.5 µm in parallel | DR-0003 island RF ground. 16 × 6.2507 pF = 100.01 pF at `cap_typ` against the ideal 100 pF. `cmim` allows at most 8 pF per instance |
| `XMis` | `pmosHV` w=512u l=1u, ng=32 (16 µm fingers) | DR-0003 island feed (the 12.8:1 bank into `bref`) |

"Bias island" is read the way DR-0003 uses the term: the `bref` node and
the chain on it (`Q3`, `R3b`, `Cbref`), plus `XMis`, the bank that feeds it.
The rest of the DR-0003 reference core is not drawn: the Stage-1 skeleton,
the Kuijk sum branch and the amp-servo loop. `realization.json` gives the
reason for every instance that is not drawn. In short, the inductors and
coupling caps belong to the matching work (#27/#56) and have no SG13G2
model; the `vb2` divider and its bypass cap are left out; so is the
reference core above. Their nets are labelled ports of this cell: `b1`,
`e1`, `outn`, `vb2`, `gsvo`, `vdd`, `vss`.

**The emitter count is a parameter.** `generate.py --nx N` (or `NX=N
layout/run_flow.sh`) redraws Q1/Q2 at `Nx=N`. Everything that depends on
the stripe span moves with it. When #58 lands, the change is one value,
not a redraw. Q3 stays at `Nx=1`. The island's density ratio is a design
quantity, and this script does not re-size it on its own.

## Provenance

**Every device is the PDK's own PyCell.** Each one comes from
`ihp-sg13g2/libs.tech/klayout/python/sg13g2_pycell_lib`, registered as
KLayout library `SG13_dev`. None is a hand-drawn footprint. `generate.py`
draws only the interconnect by hand. That means Metal1/Metal2/TopMetal1
wiring, a GatPoly bus that ties XMis's 32 gate fingers, a `ptap1`
substrate-tap rail under the `vss` rail, an `ntap1` well tap, the merged
Metal5 bottom plate of the Cbref bank, and net labels on the `<metal>.text`
layers (8/25, 10/25, 126/25). Those are the layers klt's sg13g2 extraction
deck reads for net names.

Running the PyCells headless needed three things the PDK install does not
provide:

1. **Two submodule shims.** The library imports `pypreprocessor` and
   `cni` (from `pycell4klayout-api`). IHP-Open-PDK carries both as git
   submodules, which a release-tarball fetch leaves empty. The PyPI
   `pypreprocessor` 0.7.7 sdist does not build on Python 3.14. On the
   development host, the `pycell4klayout-api` already in the PDK install was
   a different revision from the one v0.3.0 pins. `tools/fetch-pcell-deps.sh`
   therefore fetches both at the submodule commits the v0.3.0 tree records:
   `pypreprocessor@cf1ff9b` and `pycell4klayout-api@4c463c4`. It checks
   their sha256 and puts them in `layout/build/`. Nothing is installed
   host-wide.
2. **`KLAYOUT` in the environment.** The library keeps its `#ifdef KLAYOUT`
   code path only when that variable exists or a parent process is named
   "klayout". `pcell_env.py` sets it.
3. **No Tcl parameter callbacks.** `cni.dlo` runs `Calculate`-style
   parameter callbacks through tkinter and a `parameters.tcl` tree that the
   tarball does not ship. With tkinter importable, the first PyCell call
   raises and that instance draws nothing. `pcell_env.py` blocks tkinter
   while the library imports, and `generate.py` passes every parameter
   explicitly.

`klt gen --pdk-pcell` was tried first, as the klt-native route. It does not
vendor these shims, which is by design. With the shims put on `PYTHONPATH`
it crashes with an uncaught traceback instead
([klayout-tools#2944](https://github.com/2AMLogic/klayout-tools/issues/2944)).

**Reproducibility.** `generate.py` writes GDS with no timestamps and no
PCell context. Two runs give byte-identical output. The committed
`lna_core.gds` has sha256 `e2d75415…a14f`, at nx=8, written with pip
`klayout` 0.30.12 (the version klt 0.7.0 uses). `lna_core.provenance.json`
records that hash. It also records a sha256 over the PyCell library sources
(`sha256:6292d8c1…bb48`), the PDK's `.fetched-version` (0.3.0) and the two
shim commits. A different PyCell revision therefore shows up as a changed
hash rather than passing silently.

```bash
export PDK_ROOT=/path/containing   # the directory holding ihp-sg13g2/
python3 -m venv .venv && .venv/bin/pip install klayout==0.30.12
PYTHON=.venv/bin/python layout/run_flow.sh
```

`run_flow.sh` runs klt as the **PyPI release** `klayout-tools==0.7.0`,
isolated through `uvx --isolated`. A host's installed `klt` can be a
post-tag build, and the development host's was (`0.7.0+g5c94de0ebbfe`,
`is_release: false`). A plain `uvx --from klayout-tools==0.7.0` silently
reuses an installed tool of the same version, so `--isolated` is
load-bearing here. `klt_version.json` records the producing build:
`0.7.0`, tag `v0.7.0`, commit `0e2362bd`, `is_release: true`, klayout
0.30.12.

## Evidence, as recorded

All four reports pin the same layout: `provenance.input.content_hash =
sha256:e2d7541554286bb24e9efd72800bd874ae656c0d80e5630d499d501512c4a14f`.
All four name the same deck: `sg13g2`,
`sha256:bf483105cb17948270f0cad45d9418787654bfc0a5ffd04a2e2413d8c7d3b6e7`,
`released: true`. `klt env-provenance lint-envelope` finds no absolute host
paths in them.

### DRC (`drc_report.json`): `status: "violations"`, 36

`rule_counts: {"cont.width.1": 36}`. The other 38 rules this run checked
report nothing. Every finding is a non-square contact bar inside a PDK
PyCell: 17 of 1.65 × 0.16 µm (HBT collector bars), 17 of 1.52 × 0.16 µm
(HBT base bars) and 2 of 0.16 × 0.86 µm (the rppd terminal heads, rotated).
IHP's own deck checks `Cnt.a` over square contacts only
(`cont_sq = cont.not(cont.non_squares)`) and sends bars to the `CntB.*`
rules. klt's curated `cont.width.1` checks every contact. These findings
therefore come from a gap in how the deck was transcribed, and the caller
cannot clear them without editing vendor geometry. Filed as
[klayout-tools#2943](https://github.com/2AMLogic/klayout-tools/issues/2943).
They are recorded as-is. No geometry was changed to make them go away.

The coverage fields below are quoted verbatim from the envelope's `coverage`
block, as T1 item 3 requires:

- `coverage.layers_in_stream_without_rules`:
  `["1/20", "5/2", "7/21", "8/2", "8/25", "10/2", "10/25", "14/0", "26/0", "28/0", "31/0", "31/2", "32/0", "33/0", "40/0", "44/0", "51/0", "52/0", "63/0", "111/0", "126/25", "128/0", "129/0"]`
- `coverage.rules_skipped`:
  `["topmetal1.enclosing.topvia2.1", "topmetal2.enclosing.topvia2.1", "topmetal2.space.1", "topmetal2.width.1", "topvia2.space.1", "topvia2.width.1"]`.
  The same envelope's `coverage.inapplicable` gives each of these the
  reason `no_applicable_geometry`, because this cell draws no
  TopVia2/TopMetal2.
- `coverage.deck_scope`:
  `["Act", "Cnt", "Gat", "M1", "M2", "M3", "M4", "M5", "MIM", "TM1", "TM2", "TV1", "TV2", "V1", "V2", "V3", "V4"]`

The same block also carries a `voltage_domain_warnings` entry: the curated
deck applies the LV thresholds to geometry under ThickGateOx (44/0), so
XMis's HV-specific gate rules are not checked. NWell, pSD/nSD, the HBT
layers (EmWind, TRANS, Activ:mask), PolyRes/SalBlock/EXTBlock and Vmim
appear only in the without-rules list above. None of them is checked, by
construction.

**The PDK's native DRC deck was not run.** `klt drc --engine klayout --pdk
ihp-sg13g2` failed on this host. The deck aborts in
`rule_decks/feol/5_8_gatpoly.drc` (`undefined local variable or method
'absolute'`) because the standalone `klayout` on the worker is 0.28.16,
and the deck needs a newer DRC DSL. That is a host-tooling fact, and fixing
it is a worker-spec change. It is not a klt gap, since `--min-klayout-version`
exists for this case. There is no native-deck verdict in this tree.

### Extraction (`extract_report.json`)

The run recognises 32 `pfet` (XMis's fingers, L=1u W=16u, all four
terminals on the intended nets) and 16 `cap_cmim` (6.250695 pF each,
`vss`–`bref`). It finds 9 nets, which are exactly the 9 labelled ones.
Nothing is merged or dangling: `single_terminal_nets`, `dead_metal` and
`merged_net_labels` are all empty.

**Not recognised, and therefore absent from the extracted netlist:**

- The three `npn13G2` HBTs. SiGe HBT recognition is not in the curated
  deck (klayout-tools#1232, declined; reopened as
  [#2864](https://github.com/2AMLogic/klayout-tools/issues/2864), with
  per-gap issues #2860-#2863). Their terminals extract as plain nets:
  `casc`, `b1`, `e1`, `outn`, `vb2` and the `bref` diode tie.
- `R3b` (`rppd`). The curated deck takes the resistor body from GatPoly ∩
  PolyRes. The PDK's own `rppd` PyCell draws the body on PolyRes with
  **no** GatPoly under it, as IHP's LVS (`res_derivations.lvs`) expects. As a
  result, no PDK-native poly resistor is ever recognised. This is already
  filed as [klayout-tools#2679](https://github.com/2AMLogic/klayout-tools/issues/2679)
  and is reproduced here.

### LVS against `design/netlist/lna.spice` (`lvs_full_report.json`): `status: "mismatch"`

This compare uses `reference.form: "subckt-call"` with `reference.deck:
"sg13g2"`, on the design netlist exactly as committed, with
`combine_devices: true`. The two top circuits do not pair at all.
`category_counts` is `{"device.geometry_not_compared": 3, "topology": 7}`.
`counts.devices` is layout 2, reference 24, matched 0. `counts.nets` is
layout 9, reference 19, matched 0. This failure is expected: 24 of the 30
netlist instances are out of scope, and the `npn13G2` subcircuit calls pass
through as undefined abstract circuits. The run says nothing per device.
It is recorded because T1 item 4 is defined against item 1's netlist, and
this is the honest answer to that question today. `power_connectivity.status:
"unchecked"` (not a `gate-level-verilog` reference).

### LVS against the scoped reference (`lvs_report.json`): `status: "mismatch"`

`lvs_reference.py` projects the in-scope instances of `lna.spice` onto
plain-element cards in the deck's own class names. Values come from the
schematic, and the `rppd` L/W from the realization. The compare runs with
`combine_devices: true` and no parameter tolerance.

- **Matched**: `XMis`. The 32 extracted 16 µm fingers combine into one
  `pfet` L=1U W=512U against the reference `MMis bref gsvo vdd vdd pfet
  L=1U W=512U`, and nets `gsvo` and `vdd` pair.
- **Unmatched, because of extraction gaps**: `Q1`, `Q2`, `Q3` (class
  `NPN13G2`, no layout devices) and `R3B` (class `RPPD`, no layout devices).
- **Unmatched**: `Cbref`. Layout: the 16 extracted units combined into one
  `cap_cmim` of 16 × 6.250695 pF = 100.011 pF. Reference: `CBREF 100P`, the
  schematic value. The two differ by 0.011 %, and the compare is exact, so
  the cap does not pair. Its isolated `vss` net then cannot pair either,
  which accounts for the `net.merged`/`net.split` entries on `vss`. The
  `net.unmatched` entries on `b1`, `casc`, `e1`, `outn` and `vb2` are the
  HBT/R3b nets, which hold no devices on the layout side. Declaring
  `options.parameter_tolerance` does **not** rescue the pairing in this
  configuration: an isolated-net device plus unrelated device-less pins
  defeats klt's tolerance recovery. Filed with a minimal reproduction as
  [klayout-tools#2946](https://github.com/2AMLogic/klayout-tools/issues/2946).
  No tolerance is declared in the committed request, and the reference
  keeps the schematic's value rather than the realized one.
- The report's three `topology` entries do not name the class they are
  about. Filed as
  [klayout-tools#2945](https://github.com/2AMLogic/klayout-tools/issues/2945).
- Warnings, listed with the claim as T1 item 4 asks:
  `device.geometry_not_compared` for `cap_cmim` (A/P not compared, only C)
  and for `RPPD` (A/L/P/W not compared, only R). The MOS flavour (HV
  vs LV) is not part of the compare at all, because the deck reports both
  as `pfet`. `power_connectivity.status: "unchecked"`.

## What the evidence supports

- **It does support:** a committed, reproducible, parameterised GDS of 6 of
  the netlist's 30 instances, drawn from the PDK's own PyCells. The drawn
  interconnect passes every curated sg13g2 rule the run checked, apart from
  the vendor contact bars above. MIM, M1–M5, TM1 and V1–V4/TV1 all fall
  inside the deck's checked scope. The XMis bank, as drawn, extracts to the
  netlist's own device (W=512u, L=1u) on the right nets. The Cbref bank
  extracts to 100.011 pF between `vss` and `bref`.
- **It does not support:**
  - DRC clean. The curated status is `violations`, and the native deck did
    not run.
  - LVS match. Both compares are `mismatch`.
  - Any statement about the HBTs' or R3b's connectivity, because klt
    cannot see those devices.
  - Anything about the 24 undrawn instances.
  - Any T1 item.

  The ground-truth DRC for this PDK is IHP's own deck, and that run is
  still missing.

## Signoff citations

`signoff/manifest.json` cites `drc_report.json` for **item 3** and
`lvs_full_report.json` for **item 4**, both pinned to the GDS hash above.
Both render `unmet` / `check_failed`, which records that the evidence
exists and fails. Neither is a claim. **Item 2 is deliberately uncited.**
A layout of 6 of 30 instances does not back "Layout" for the block. Item 2
accepts any passing envelope (klt cannot check topical relevance), so
citing `extract_report.json` would turn the row `met` on a partial layout.

A future fix to klayout-tools#2943 could make this partial layout DRC-clean
under the curated deck. Then item 3 would render `met` for a cell that is
not the block. Before re-running the flow under such a klt, either complete
the layout scope or withdraw the item-3 citation. The same applies to item
4 if #2864 and #2679 both land.

## CI: layout-freshness

The `layout-freshness` job in `.github/workflows/signoff.yml` runs
`.github/scripts/check-layout-freshness` (self-test first:
`.github/scripts/test-check-layout-freshness.sh`). It needs only bash and
python3 stdlib: no klayout, klt or PDK. It fails, naming the relationship, if:

1. `sha256(lna_core.gds)` differs from `gds_sha256` in
   `lna_core.provenance.json`;
2. regenerating the LVS reference with `layout/lvs_reference.py` from the
   current `design/netlist/lna.spice` (in a temporary repo-shaped copy) is not
   byte-identical to the committed `lna_core.lvs_reference.spice` (this also
   catches a netlist edit that leaves a device outside the instance
   partition);
3. `provenance.input` in `drc_report.json` or `lvs_full_report.json` is
   missing, has a `role` other than `layout`, or has a `content_hash` that is
   not `sha256:` plus the committed GDS hash.

Regenerating the GDS and re-running the reports stays a deliberate local
step (`layout/run_flow.sh`); CI only checks that the committed files agree.
